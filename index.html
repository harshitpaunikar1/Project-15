Notebook-to-Tool Walkthrough / Flask Salary Estimation Deployment

The Interesting Part Starts After model.fit()

A notebook can give you coefficients. A usable tool has to define inputs, serialize the artifact, expose a route, render a response, and survive an environment that did not train the model. That is the real story in this folder.

Rows in Training CSV 8
Input Fields 3
POST Endpoints 2
Serialized Artifact 1 pickle

What The Repo Actually Ships

  • model.py trains a linear regression and writes model.pkl.
  • app.py exposes /, /predict, and /predict_api.
  • request.py demonstrates the JSON path with one hard-coded request.
  • The browser form collects experience, test score, and interview score, then renders a single salary string.
I do not think this folder is interesting because the model is sophisticated. It is interesting because it forces notebook logic to make contact with real inputs, real route handling, and real deployment fragility.
commit 01

Define the software surface before talking about deployment

The most valuable move in this project is not mathematical. It is architectural. The repository stops being a training exercise the moment it draws a line between model creation and model use. That line is simple here, but it is real: model.py creates an artifact, app.py loads it, and the template in templates/index.html becomes the human-facing entry point.

That may sound obvious, but I have seen plenty of ML portfolios dodge exactly this step. They show a notebook, maybe a chart, maybe an accuracy metric, and then quietly hope the reader will imagine a product around it. This folder does not make that mistake. A candidate enters three values, hits submit, and receives a number. There is also a separate API endpoint for machine-to-machine access. Neither surface is elaborate, but both are concrete.

The right way to read the app is as a sequence of obligations. The browser must collect input in a stable shape. Flask must coerce that input into a numeric array. The model artifact must already exist and load successfully. The return value must be formatted into something a user can understand. Every one of those obligations is a place where notebook confidence gets cut down to size.

Folder Evidence

  • hiring.csv has 8 rows and 4 columns.
  • The template collects three text inputs.
  • The app exposes one human path and one API path.

Why I Care

Interface shape is where toy models reveal their assumptions. If you cannot state the accepted inputs precisely, you do not yet have a deployable object.

commit 02

Train something serializable, and admit how small it is

The model itself is a plain linear regression trained on three features: experience, test score, and interview score. The dataset is tiny. That matters more than the algorithm choice. With only eight records, the author sensibly avoids a train-test split and fits on the full table, but that means any quality number you quote is describing fit on known data, not proven behavior on new candidates.

The preprocessing is straightforward. Missing experience is filled with zero. Missing test score is filled with the column mean, which works out to roughly 7.86. Experience tokens such as five, two, ten, and eleven are mapped into integers through a hand-written dictionary. After that, the model is fit and pickled.

I like this because it is honest about the dataset it has. I do not like it when people pretend a fragile dataset becomes mature just because it got wrapped in scikit-learn. On the recomputed training set, the linear regression reaches an R² of about 0.964. That sounds high until you remember the sample size. Eight rows are enough to build a demo. They are not enough to justify salary-setting confidence.

dataset = pd.read_csv("hiring.csv")

dataset["experience"] = dataset["experience"].fillna(0)
dataset["test_score"] = dataset["test_score"].fillna(
    dataset["test_score"].mean()  # replace the lone missing score
)

word_dict = {
    "one": 1, "two": 2, "three": 3, "four": 4,
    "five": 5, "six": 6, "seven": 7, "eight": 8,
    "nine": 9, "ten": 10, "eleven": 11, "twelve": 12,
    "zero": 0, 0: 0
}

dataset["experience"] = dataset["experience"].apply(
    lambda x: word_dict[x]  # convert written years into integers
)

X = dataset[["experience", "test_score", "interview_score"]]
y = dataset["salary"]

regressor = LinearRegression()
regressor.fit(X, y)
pickle.dump(regressor, open("model.pkl", "wb"))

The recomputed coefficients also tell a familiar tutorial story. Experience contributes the largest per-unit lift at roughly 2827.63. Interview score adds about 2196.98 per point. Test score adds about 1912.94. That ordering feels plausible, but again, plausibility is not the same thing as robustness. With data this small, one extra row can easily move the line.

Practical Read

The model is not the product. It is a compact artifact that makes the route worth testing.

Common Mistake

Quoting a training-set R² as if it were deployment evidence. It is not. It only tells you the line hugs the eight rows it already saw.

commit 03

Wire the browser route, then notice the input contract it creates

The HTML form in the Flask template is simple enough to read in a glance. Three text boxes. One submit button labeled SALARY. A placeholder line for {{ prediction_text }}. That economy is good for a demo because there is nowhere for the flow to hide. You can see exactly what the application asks of the user.

The sharper detail lives in app.py. The browser route does not read field names individually. It grabs request.form.values(), casts every value to int, wraps the result in a NumPy array, and sends it directly to the model. That is concise. It also creates a strict and mostly undocumented contract: the form must keep the feature order stable, every incoming value must be integer-like, and the user must already understand that experience should be entered numerically even though the training file originally stored many experience values as words.

That last point is the kind of thing practitioners notice and generic writeups skip. In the training script, experience is cleaned from tokens like five and ten. In the web app, int(x) means the browser flow now expects 5 and 10. That is a perfectly defensible simplification. It is also a change in interface semantics, and deployment work is exactly where those semantic shifts have to become explicit.

@app.route("/predict", methods=["POST"])
def predict():
    int_features = [int(x) for x in request.form.values()]
    final_features = [np.array(int_features)]
    prediction = model.predict(final_features)

    output = round(prediction[0], 2)
    return render_template(
        "index.html",
        prediction_text=f"Estimated salary is ₹ {output}"
    )

I would keep the route this small in a teaching project. I would not keep it this trusting in a real deployment. There is no range checking, no message for malformed input, no distinction between missing values and impossible values, and no explanation of the currency context behind the rupee symbol. None of that invalidates the demo. It just tells you what stage of maturity the demo is in.

Input Mismatch

Training tolerates written experience values. The browser route does not. That is not a bug by itself, but it is a design decision worth naming.

commit 04

Add an API, but do not pretend that one endpoint makes a platform

The API route is useful because it proves the app can be consumed without the browser. request.py posts a JSON body to http://localhost:5000/predict_api, and the Flask handler returns a numeric JSON response. That is enough for local testing and enough to demonstrate that the model can sit behind another service later.

It is also a good example of where demo ergonomics and production reliability diverge. The route turns the JSON payload into a list by calling list(data.values()). That assumes the sender preserves key order in the same order the model expects features. The included request script does exactly that, so the demo works. A stricter implementation would name the fields explicitly, validate them, and reject malformed payloads with a readable error. I would push for that immediately if this were headed toward shared internal use.

This is why I resist glamorous deployment language. A Flask wrapper is not the finish line. It is the first moment when the model is forced to declare its contract. The route here is perfectly adequate for a portfolio demonstration. It is not yet a dependable service interface, and calling it one would lower the editorial standard of the page.

@app.route("/predict_api", methods=["POST"])
def predict_api():
    data = request.get_json(force=True)
    prediction = model.predict([np.array(list(data.values()))])

    output = prediction[0]
    return jsonify(output)

# request.py sends:
# {"experience": 2, "test_score": 9, "interview_score": 6}

There is still value here. A lot of beginner deployments never separate human interaction from machine interaction at all. This one does. The reader can see the two surfaces, compare them, and understand that the same model can answer both. That is a solid notebook-to-tool lesson.

Good Enough For

Local demoing, route comprehension, and proving that the artifact can answer both HTML and JSON callers.

Not Good Enough For

Stable internal APIs, audited compensation workflows, or any workflow that needs explicit validation, logging, or permissions.

commit 05

Deployment becomes real when environment friction shows up

The folder’s most honest line may be Flask’s own warning: the built-in server is a development server and should not be used for production deployment. That warning matters because the project has reached the point where environment details suddenly matter. The app loads model.pkl at import time. It relies on local file paths. The repository does not include a dependency manifest. The README tells the user to open an Anaconda prompt and run python app.py, which is practical advice for a tutorial and incomplete advice for an operational handoff.

Pickle is the other deployment hinge. It is fast to use, common in tutorials, and tightly coupled to the environment that created the artifact. I have no problem with pickle in a small local demo. I do have a problem when people mistake it for a portability guarantee. If the package versions drift, loading the artifact can become the failure point before a single request is served. The route code is not where deployments usually break first; the artifact boundary often is.

The folder also runs the app with debug=True. That is fine for iteration. It is not a detail to quietly carry into a serious hosting story. Debug mode, missing schema validation, no tests, no evaluation report, no requirements file, and a dataset of eight rows all push the same conclusion: this is a useful interface prototype, not a salary decision system.

What Exists Why It Matters What Is Still Missing
Browser form and Flask template A human can actually submit values and receive a result. Validation, explanatory error states, and units guidance.
/predict_api JSON route The model can be called by a script, not just a page. Explicit field mapping, schema checks, and response envelope design.
Serialized model.pkl The inference app is separated from training code. Version pinning, artifact metadata, and safer deployment packaging.
Small training script The preprocessing logic is readable and easy to reproduce. Holdout evaluation, tests, and any fairness or compensation review.
The right conclusion is not “this is too small to matter.” The right conclusion is “this is exactly big enough to expose the engineering work a notebook usually hides.”

Operational Reading

Once a model artifact is loaded at app startup, dependency drift becomes an application problem, not just a notebook problem.

Editorial Rule

Never let a deployment page imply production readiness just because a localhost route responds.

commit 06

Use the demo for what it is good at, then tighten the weak seams

This project earns its place as a deployment walkthrough because it gets one thing right that many beginner ML repos never reach: it turns a trained estimator into a callable surface. That is not glamorous work. It is the necessary work. The folder defines a form, a request path, an artifact boundary, and a returned result. Those are the pieces another human can inspect, use, and improve.

If I were carrying this forward, I would keep the overall simplicity and harden the seams. I would replace the positional input assumptions with named extraction. I would validate types and ranges before prediction. I would save artifact metadata next to the model so environment mismatches are easier to diagnose. I would add a small evaluation note explaining that the model was trained on eight rows and is intended as a tutorial artifact, not a compensation authority. And I would separate “deployment proof” from “prediction quality” in the project narrative, because they are not interchangeable claims.

The practical lesson is sharp: wrapping a model in Flask is not impressive because Flask is magical. It is useful because the wrapper forces the model to stop being abstract. Once inputs, routes, files, and runtime assumptions are visible, you can finally judge what has really been built.
